# Written plans

Read this procedure when creating or revising a written task plan or roadmap. The main skill determines when a plan is needed and governs execution, continuation and completion. [Plan lifecycle](plan-lifecycle.md) owns shared identities, destinations, name references and state transitions. [Roadmaps](roadmaps.md) supplies the additional coordination rules for umbrella work and its members; standalone plans need no roadmap.

## Plan contents

Write for a reader who does not have the task conversation. Include the following information where relevant; combine sections naturally rather than creating empty headings or imposing a fixed template.

| Information | Required result |
| --- | --- |
| Task and motivation | Explain what is to change, which problem it solves and why the work matters. |
| Outcomes and boundaries | Identify intended results, included work and explicit exclusions. |
| Agreed decisions and constraints | State the decisions and limitations the work must preserve, with relevant supporting references. |
| Open questions | Separate confirmed facts from assumptions and unresolved questions; explain consequences for the approach, authorization or ability to proceed. |
| Stages | For each meaningful stage, identify its result and how readiness will be checked. Show dependencies where they affect the order of work. |
| Overall completion criteria | Define the observable conditions for the task to be complete, with necessary source, requirement and research references. |

Derive the plan from the request and available evidence. Investigate consequential unknowns when needed; a plan does not require a research stage merely to fill a template. Do not invent a rationale, settled decision or verification result to make the document appear complete.

## Readiness of the plan

Plan preparation is complete when a new reader can identify the intended outcome, boundaries, agreed constraints, unresolved blockers, next permitted step and evidence needed to establish completion.

A useful plan may still contain questions that block implementation. Mark their effect and the decision or investigation needed to resolve them; distinguish a plan ready for discussion from work ready for execution. Planning authorization alone does not settle those questions or authorize implementation.

Record dependencies, blockers and the next step where relevant; that step can be a decision or investigation rather than implementation. Future work uses the lifecycle procedure rather than a separate copy of the plan. When work is authorized, use the main skill's [start/resume procedure](SKILL.md#start-or-resume) to check an older plan against current circumstances before acting on it.
